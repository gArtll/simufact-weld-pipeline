# Validation

What is verified, and where the evidence lives.

**In this repository (reproducible by anyone, no commercial software):** the CI tier -- unit and integration tests,
two synthetic example cases taken through `prep` and `gate --self`, the regression table of the input check, and the
data scanners. Every input it uses is synthetic and generated by a script in the repository.

**Against real models (evidence kept outside the public repository):** the tool was developed against real welding
models -- a T joint (web on a curved plate, two-sided fillets) and a tube on plate (closed ring) -- with GUI-built
Simufact reference projects and full welding + cooling solver runs. Their geometry, meshes, process parameters, solver
logs and results are not published. What they established is written down as method: rules in
`common/rules.yaml` / [`rules.md`](rules.md), the failure localisation method in `AGENTS.md`, the scripting pitfalls
in [`simufact-api-notes.md`](simufact-api-notes.md), and the findings below, without their numbers.

No experimental calibration: heat sources are literature or screening values.

## What the real-model work established (method only)

| Topic | Finding |
|---|---|
| headless bead mounting | a scripted bead imported as geometry and activated by the heat source solves normally; a bead whose mesh and weld line do not coincide with the reference is not comparable |
| input check | the five key `.dat` sections of a headless project matched the GUI reference once the trajectory patch, contact table and window rules (R6', R14, R19, R22) were in place; the orientation table agreed within the ORIENT tolerance |
| independent bead | node snapping removes the 10 µm near-coincidence band; same-section peak temperatures of tool bead and reference bead agreed within the 5 % limit |
| closed ring | the ring window, closed bead and process-default contact reproduced the GUI reference input (`.dat`) of a tube-on-plate study; a short solve ended normally and matched its same-section peak temperature within the limit |
| one-way contact | a repeated exit 3015 was localised to cross-gluing at a micrometre near-coincidence of a bead root node and a web corner node under two-way contact detection; bead -> component contact first-to-second removed it. Side effects of that change are real and must be reported (higher peak temperature and t8/5 near the weld); the direction is stated here, the values are not published |
| exit 3004 is not "clean" | a GUI reference run ended with exit 3004 at 100 % and still had one element inside out at the weld root, recovered by the solver; `run/solver_stats.py` reports that as *PASS with warnings* |
| mesh cost | on one geometry, a weld-refined base mesh cost more per increment than its element ratio, with the same increment count; a peak temperature read at the nearest node does not transfer between two meshes whose nodes are a millimetre apart where the gradient is steep -- `post` probes by physical coordinate and refuses a point the mesh cannot represent |

## What CI verifies on every push

| Check | What it proves |
|---|---|
| `pytest tests` | provenance and lifecycle rules, STEP joint classification and capability planning (T joint supported; butt / lap detected, not supported), the local joint frame (a rotated T joint gives the rotated bead, < 1e-6 mm), the explicit web mesher and both plate backends (swept, mapped onto oblique faces), contact planning (CT1), the solver-log verdicts on synthetic PASS / PASS with warnings / FAIL logs, the scanners themselves |
| `prep` + `gate --self` on `example_synthetic` | two-sided fillet beads on a web: root lines, bead mesh, outer weld lines, detJ, near-coincidence band, a self-assembled `.dat` passing the input check |
| `prep` + `gate --self` on `example_tube_synthetic` | the closed-ring variant: radial section frame, closed bead, ring window length (R19) |
| `gate/run_regressions.py` | the input check's regression table; its cases need stored `.dat` files, which are not in the public repository, so on CI they are skipped -- the check is that nothing is *inconsistent* |
| `check_no_absolute_paths.py`, `check_private_data.py` | no machine paths, credentials, internal model names or unregistered data files in the tree or the pushed commit messages |

Solver-log verdicts (`run/solver_stats.py`, `tests/failure_logs/`): all four logs are synthetic, written by
`make_synthetic.py` in the Simufact / MARC line formats. The FAIL pair shows the usual exit-3015 signature -- the time
step cut to its minimum, elements inside out in adjacent groups, separation warnings dominating. That signature is a
place to look first, not a diagnosis.

`pst` and `rst` in the `.sts` table are post file and restart file write counters. They follow the write-every-N
setting, not the solver's behaviour; a cut-back increment shows up as a repeated increment number.
